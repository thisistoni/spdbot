### P0 — Browser upload staging, with an unresolved Windows limit

Use final merged [`6656b9e24`](https://github.com/milind-soni/OpenMausBot/commit/6656b9e240ce3d64192d0f152294f909668f896f), [PR #3716](https://github.com/milind-soni/OpenMausBot/pull/3716), as the source for a bounded manual port.

The fork validates paths and sometimes creates hard links; unnamed workspace files can remain live paths while Chrome starts or a picker waits. Upstream stages private copies before those waits, makes staging asynchronous, opens descriptors before copying, bounds sizes and cleans a failed batch. Preserve attachment display names and await every caller. `shared/upload-limits.ts` and boxed-browser assumptions in this patch are newer than the fork; add/adapt only the necessary helper and desktop paths, not the Cloud/browser-box subsystem.

**Do not trust the title or old PR body:** the final merge appended a change that allows Windows workspace and named-attachment uploads again. Its Windows `openUpload` uses `O_RDONLY`, without handle-final-path validation; Linux uses descriptor-path checks and macOS uses no-follow flags. Staging shortens the Windows race but does not establish protection against a junction swap before open. Decide and prove the Windows boundary in implementation; do not claim the earlier blanket refusal is the merged behavior or silently disable existing uploads.

Tests: `browser-upload-security`, `browser-upload`, `host/browser`, browser-viewer and internal browser-call tests. Include named attachments and workspace files on real Windows, macOS parent/symlink swaps, pre-open Windows junction swaps, waits, limits and partial cleanup. This is the most involved security port in the first batch.
